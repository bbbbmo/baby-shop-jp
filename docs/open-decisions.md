## A. 사업 결정

### A-1. 한국 배송비 정책 · **미정**

지금 코드는 일본 기준 상수 한 쌍만 있습니다 (`5,000엔 이상 무료 / 550엔`).

정해야 할 것
- 한국 무료배송 기준 금액
- 한국 배송비

**잠정값으로 진행합니다**: `30,000원 이상 무료 / 3,000원`
`src/shared/config/markets.ts` 한 파일에 모아두고 주석으로 잠정임을 표시합니다.
확정되면 그 두 줄만 고치면 됩니다.

**코드는 준비되었습니다.** `src/shared/config/markets.ts`의 `MARKET_CONFIG.kr`에
잠정값(30,000원 이상 무료 / 3,000원)이 들어 있습니다. 확정되면 그 두 줄만 고치면 됩니다.

### A-2. 일본 배송비 유지 여부 · **미정**

현행(`5,000엔 / 550엔`)을 그대로 둘지, 이참에 조정할지.
그대로 두는 것으로 가정하고 진행합니다.

### A-3. 상품별 원화 가격 · **미정**

한국은 국내 판매라 일본가(대행 수수료·국제배송 포함)와 다릅니다.
상품마다 원화 가격을 정해야 합니다.

**구현을 막지 않습니다.** 원화 가격이 비어 있는 상품은 한국 화면에 나오지 않도록 설계했습니다.
가격을 채운 상품부터 순서대로 한국 마켓에 공개할 수 있습니다.

**입력할 수 있게 되었습니다.** 관리자 상품 등록·수정 화면에 「판매가 (원)」과
「정가 (원)」이 생겼습니다. 비워두면(0) 그 상품은 한국 마켓에 노출되지 않습니다.
판매가와 정가는 함께 채우거나 함께 비워야 합니다.

### A-4. 한국 마켓 최초 공개 상품 범위 · **미정**

전 상품을 한 번에 열지, 일부만 먼저 열지.
A-3과 함께 결정하면 됩니다.

## B. 외부 신청 · 발급

### B-1. 도로명주소 API 키 · **해결됨**

- 발급처: juso.go.kr — **팝업 API** (`popupApi.do`)
- 비용: 무료 (가입 필요)
- 환경변수 이름: `JUSO_API_KEY`

**승인키는 API별·도메인별로 따로 발급됩니다.** 검색 API(`addrLinkApi.do`) 키와
팝업 API(`addrLinkUrl.do`) 키는 서로 통하지 않고, 바꿔 쓰면 `E0001 승인되지 않은 KEY`가
납니다. 우리가 쓰는 건 **팝업 API 키**입니다.

**실제 동작을 확인했습니다.** `/kr/checkout`에서 주소 칸(또는 「주소 검색」 버튼)을 누르면
juso 팝업이 뜨고, 「테헤란로 152」로 검색해 고른 주소가 우편번호·시도·시군구·도로명주소로
채워지는 것까지 브라우저에서 확인했습니다.

현재 키는 juso의 **개발용(dev) 키**라 유효기간이 있습니다. 실서비스 도메인이 정해지면
운영 키를 그 도메인으로 재발급해야 합니다 (C-1과 함께).

### B-2. 결제대행사 계약 · **조사 중**

`payment-plan-explainer.md`의 체크리스트를 참고하세요. 요약하면

- [ ] **법인사업자인가 개인사업자인가** ← 가장 급함. 일본 편의점 결제는 법인만 가능
- [ ] 엑심베이 일본 결제수단 범위 (카드·편의점·PayPay 외)
- [ ] 엑심베이가 한국 결제(카카오페이·네이버페이)도 되는지
- [ ] 일본·한국 각각의 수수료율
- [ ] 현금영수증·에스크로 처리 여부

**결제 구조는 준비되었습니다.** `docs/specs/2026-09-03-payment-abstraction-design.md`의 설계로
결제 계층이 들어갔고, 계약 전까지는 가짜 결제사(mock)로 전 구간이 동작합니다.
PG사가 정해지면 `src/shared/api/payments/providers/`에 파일 하나를 추가하고
`registry.ts`와 `catalog.ts`에 각각 한 줄씩 더하면 됩니다.

한국 결제는 **국내 PG사 한 곳과 직계약**하는 것으로 방향이 잡혔습니다. 네이버페이·카카오페이는
그 PG가 제공하는 결제수단으로 들어옵니다.

남은 확인 사항
- [ ] 어느 PG사인가 (토스페이먼츠 · 나이스페이 등)
- [ ] 결제사가 가맹점 서버 IP 신고를 요구하는가 (배포처 결정과 엮입니다)
- [ ] 현금영수증 · 에스크로를 대행사가 처리하는가
- [ ] 일본 결제와 한국 결제의 수수료율

### B-4. 배포처 · **미정**

`SITE_URL` 환경변수가 결제 복귀 URL의 오리진을 정합니다. 배포처가 정해지면 그 값을 `.env`에
넣습니다. 넣지 않으면 요청 URL의 오리진을 씁니다 — 로컬 개발은 그대로 동작합니다.
URL이 아닌 값을 넣으면 결제 시작 시점에 바로 예외가 납니다. 조용히 잘못된 주소로 가는 것보다
낫다고 보았습니다.

### B-5. 비회원 결제 인가 규칙 · **정해짐**

결제 시작(`POST /api/payments/start`)은 **주문번호와 이메일이 모두 맞아야** 진행됩니다.
주문 조회(`get_order_by_number_and_email`)가 이미 같은 규칙을 쓰고 있어 그것을 맞춘 것입니다.

주문번호만으로 열어 두면 주문번호를 아는 사람이 남의 주문 상태와 금액을 알아낼 수 있고,
결제 시도 행을 계속 쌓을 수도 있습니다. 주문번호는 비밀이 아닙니다 — 확인 메일, 화면,
문의 캡처에 그대로 남습니다.

로그인 회원도 같은 규칙을 지납니다. 회원 전용 경로를 따로 두지 않았습니다.

### B-3. Supabase 로그인 복귀 주소 추가 · **필요**

주소가 `/jp/...`, `/kr/...`로 바뀌므로 소셜 로그인 후 돌아올 주소를 등록해야 합니다.

- Supabase 대시보드 → Authentication → URL Configuration → Redirect URLs
- `/jp/auth/callback`, `/kr/auth/callback` 추가

카카오·구글·라인 쪽은 손대지 않아도 됩니다. 그쪽은 Supabase 주소를 보고 있습니다.

**코드는 준비되었습니다.** 소셜 로그인이 `/jp/auth/callback`, `/kr/auth/callback`으로 돌아옵니다.
Supabase 대시보드에 이 두 주소를 등록하기 전까지 소셜 로그인이 실패합니다.

## C. 운영 정책

### C-1. 실제 도메인 · **미정**

아직 도메인이 없습니다. 설계 문서와 설명 문서에서 `como.com`을 예시로 쓰고 있습니다.
정해지면 문서의 예시 주소를 교체합니다.

구현에는 영향이 없습니다. 주소 뒤에 `/jp`, `/kr`을 붙이는 구조라 도메인이 무엇이든 그대로 동작합니다.

### C-2. 첫 화면 기본 마켓 · **구현됨**

`/`로 들어온 손님을 어디로 보낼지.

**브라우저 언어 설정으로 추정**해서 `/jp` 또는 `/kr`로 보냅니다.
추정이 틀려도 화면 위쪽에서 바꿀 수 있으므로 갇히지 않습니다.

한국어·일본어 둘 다 아닌 경우(영어 등) 어디로 보낼지는 정해야 합니다.
→ **일단 `/jp`로 보냅니다.** 기존 서비스가 일본 대상이었기 때문입니다.

`src/app/page.tsx`에 구현되었습니다. 브라우저 언어가 `ko`로 시작하면 `/kr`,
`ja`로 시작하면 `/jp`, 그 외에는 `/jp`로 보냅니다.

### C-4. 루트 페이지의 마켓 선택 화면 · **구현됨**

`/`에 들어오면 일본어·한국어 중 하나를 고르는 화면이 뜹니다 (`src/app/page.tsx`).
브라우저 언어로 자동 이동하던 동작은 없앴습니다. **`/`는 언제나 선택 화면입니다.**

선택지에는 언어만이 아니라 **통화와 배송지를 함께** 적습니다. 마켓을 잘못 고르면
가격과 배송 국가가 통째로 달라지므로, 무엇을 고르는 것인지 드러나야 하기 때문입니다.

돌아가는 길은 **푸터의 작은 링크**(`日本語 / 한국어`) 하나입니다.
화면마다 토글을 두는 것보다 조용하면서, 나라를 잘못 고른 사람이 갇히지 않습니다.

고른 값은 **기억하지 않습니다.** 쿠키를 쓰지 않으므로 `/`로 오면 항상 다시 묻습니다.
재방문자는 보통 `/jp`·`/kr`을 북마크하거나 공유 링크로 들어오므로 `/`를 다시 거치는
일이 많지 않다고 보았습니다. 실제로 불편이 확인되면 그때 기억 기능을 넣으면 됩니다.

### C-3. 두 마켓 매출을 어떻게 합쳐 볼지 · **미정**

결제대행사를 나라별로 나누면 관리 화면이 두 개가 됩니다.
매출을 합쳐 보려면 별도 정리가 필요합니다.

결제 스펙에서 다룹니다. 지금 구현에는 영향 없습니다.

## D. 이전 작업에서 남긴 것

회원가입 최소 수집 + 동의 기록 작업(완료·병합됨)에서 의도적으로 남긴 항목입니다.
전부 급하지 않습니다.

### D-1. 동의 저장 실패 시 화면이 멈춤

동의 화면에서 저장이 네트워크 오류 등으로 실패하면
버튼이 "처리 중" 상태에서 멈추고 오류 안내가 뜨지 않습니다.
기존 회원가입 폼도 같은 구조라 이 작업이 만든 문제는 아닙니다.

### D-2. 동의 화면 직접 접근 시 기록이 중복됨

이미 동의한 사람이 `/auth/consent` 주소로 직접 들어가 다시 제출하면 기록이 한 벌 더 쌓입니다.
동의 기록은 이력을 쌓는 구조라 데이터가 깨지지는 않습니다.

### D-3. 동의 화면을 이탈하면 다시 묻지 않음

소셜 로그인 첫 회에 동의 화면에서 나가면, 다음 접속 때 다시 뜨지 않습니다.
막으려면 모든 화면에 검사를 넣어야 해서 범위가 커집니다.

### D-4. 카카오 이메일 미동의 계정

카카오는 이메일이 선택 동의라, 거부하면 이메일 없는 계정이 생깁니다.
이 회원은 주문 조회에서 이메일로 비회원 주문을 연결하는 기능을 쓸 수 없습니다.
카카오에서 이메일을 필수 동의로 올리려면 비즈 앱 전환과 검수가 필요합니다.

### D-6. 한국어 화면의 첫 응답에 언어 표시가 일본어로 나감 · **해결됨**

화면 언어는 경로가 정하는데, 브라우저에 처음 내려가는 HTML의 언어 표시(`lang` 속성)는
`src/app/layout.tsx`에서 항상 `ja`로 고정되어 있습니다. 화면이 뜬 직후 자바스크립트가
바로잡으므로 **일반 사용자에게는 문제가 없습니다.**

다만 자바스크립트를 실행하지 않고 첫 HTML만 읽는 쪽 — 화면 낭독기 일부, 검색 로봇,
링크 미리보기 — 은 `/kr` 화면을 일본어로 인식합니다.

제대로 고치려면 `src/proxy.ts`가 경로에서 마켓을 읽어 넘겨줘야 합니다.
그 파일은 로그인 세션 갱신을 맡고 있어 조심스러운 곳이라, **2단계에서 함께 다룹니다.**

**해결했습니다.** `src/proxy.ts`가 경로에서 읽은 마켓을 요청 헤더로 넘기고,
루트 레이아웃이 그것으로 `lang`을 정합니다. 로그인 세션이 유지되는 것도 확인했습니다.

### D-5. 오래된 문서·경고

- `README.md`의 디자인 설명과 폴더 구조가 현재 코드와 다릅니다
- `src/shared/i18n/FontModeProvider.tsx`에 코드 검사 경고 1건이 남아 있습니다
