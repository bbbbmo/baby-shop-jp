# 이용약관 · 개인정보처리방침 설계

작성일: 2026-09-01

## 목표

회원가입에서 동의를 받는 두 문서를 실제 내용으로 채우고, 가입 흐름을 벗어나지 않고 읽을 수 있게 한다.

지금은 `/terms`와 `/privacy` 둘 다 「준비 중입니다」만 뜨는 껍데기다. 동의 체크박스는 있는데
무엇에 동의하는지 볼 수가 없다.

## 먼저 — 이 문서는 그대로 쓸 수 없다

**법적 구속력이 있는 문서이고, 지금 채울 수 없는 필수 기재사항이 있다.** 초안은 전자상거래법과
개인정보보호법의 요구 항목을 따라 구조를 갖추지만, **최종본은 전문가 검토를 받아야 한다.**

채워야 하는데 아직 없는 값

| 항목 | 근거 |
| --- | --- |
| 상호 · 대표자명 | 전자상거래법 제10조 |
| 사업자등록번호 | 같음 |
| 통신판매업 신고번호 | 같음 |
| 사업장 주소 · 전화 · 이메일 | 같음 |
| 개인정보 보호책임자 이름 · 연락처 | 개인정보보호법 제31조 |
| Supabase 프로젝트 리전 | 국외 이전 고지 판단에 필요. 대시보드 → Settings → General → Region에서 확인 |
| 결제대행사 · 배송사 상호 | 처리위탁 고지 |

이 값들은 **감추지 않고 본문에 그대로 드러낸다** — 아래 「빈칸 정책」 참고.

---

## 표시 방식 — 상태 모달, 인터셉팅 라우트 아님

Next의 Parallel Routes + Intercepting Routes(`@modal` 슬롯 + `(.)` 규칙)를 쓰면 "앱 안에서는 모달,
직접 접속하면 페이지"가 되지만 **쓰지 않는다.**

이유는 하나다. 인터셉팅 라우트는 모달을 열 때 **URL을 `/kr/terms`로 바꾼다.** 회원가입 도중에
새로고침하거나 뒤로가기를 잘못 누르면 입력하던 이메일·비밀번호·이름이 날아간다. 사진 갤러리에서는
스크롤 위치만 잃지만 가입 폼에서는 손해가 크다.

그 대가로 얻는 건 모달의 공유 가능한 URL과 북마크인데, **약관 모달은 공유할 대상이 아니다.**
공유가 필요하면 페이지 주소가 이미 있다.

구조상으로도 `signup`이 `(main)` 그룹 밖이라 두 곳을 덮으려면 슬롯을 `[market]/layout.tsx`에
둬야 하고, Next 16부터는 슬롯마다 `default.tsx`가 없으면 빌드가 실패한다. 얻는 것에 비해 비싸다.

### 페이지는 유지한다

모달을 만들어도 `/terms`와 `/privacy`는 남긴다. **인터셉팅 때문이 아니라 법 때문이다** —
약관은 상시 열람·보관이 가능해야 한다. 고객 응대나 메일에서 「약관 보기」 링크를 보낼 곳도 필요하다.

**푸터에 두 링크를 추가한다.** 지금 없다. 푸터에서는 **모달이 아니라 페이지로 이동**한다 —
푸터를 누르는 사람은 문서를 읽으러 온 것이고, 지킬 입력값도 없다.

### 모바일 뒤로가기

모달을 열 때 히스토리 항목을 하나 넣어, 뒤로가기가 가입 화면을 벗어나지 않고 모달만 닫게 한다.
CLAUDE.md가 모바일 우선이고, 휴대폰 사용자는 모달을 뒤로가기로 닫으려 한다.

## 본문은 한 곳, 표시는 두 곳

모달과 페이지가 같은 데이터를 렌더한다. 문구가 갈라질 일이 없다.

```
src/entities/legal/
  index.ts
  content/terms.ko.ts       content/terms.ja.ts
  content/privacy.ko.ts     content/privacy.ja.ts
  model/documents.ts        타입 · 로케일별 조회 · 빈칸 검출
  model/documents.test.ts
  LegalDocumentBody.tsx     본문 렌더 (조·항)
  LegalModal.tsx            모달 껍데기
```

`entities` 레이어에 두는 이유는 `features/signup-form`(feature → entity)과
`widgets/footer`(widget → entity), `app`의 두 페이지가 모두 쓰기 때문이다. 모두 허용된 방향이다.

### 데이터 모양

```ts
export type LegalSection = {
  heading: string;
  paragraphs: string[];
};

export type LegalDocument = {
  id: "terms" | "privacy";
  title: string;
  // user_consents.terms_version과 같은 값이어야 한다. 지금은 둘 다 "v1".
  version: string;
  effectiveDate: string;
  sections: LegalSection[];
};
```

문단을 문자열 배열로 두는 이유는 렌더가 단순해지고 조항 번호를 본문에 그대로 쓸 수 있어서다.
마크다운 파서를 끌어들일 만큼 서식이 복잡하지 않다.

### 빈칸 정책

모르는 값은 본문에 **`［사업자등록번호 미입력］`** 처럼 그대로 보이게 둔다. 배포본에서도 보인다.

표기는 **전각 대괄호 `［ ］` 안에 「항목명 + 공백 + 미입력」**으로 고정한다. 일반 대괄호는 본문에서
쓰일 수 있어 오검출이 난다. `findPlaceholders`는 `/［([^］]+)\s미입력］/g`로 찾는다.

조용히 빼면 법정 기재사항이 빠진 줄 모르고 배포한다. 눈에 보이면 채우게 된다. 「미입력」이라고
적혀 있는 편이, 항목 자체가 없어서 무엇이 빠졌는지도 모르는 것보다 낫다.

`findPlaceholders(document): string[]`를 순수 함수로 빼서 테스트로 고정한다. 개발 환경에서는
문서 위에 미입력 항목 목록을 배너로 띄우되, **`LegalDocumentBody` 안에 둬서 모달과 페이지 양쪽에
같이 나오게 한다.** 한쪽에만 있으면 못 보고 지나친다.

## 문서 구조

### 이용약관 (`terms`)

전자상거래 표준약관을 따르되 **이 가게의 실제 사정에 맞춘다.** 특히 일본 고객에게는 구매대행
형태로 제공하므로, 청약철회와 배송 조항이 국내 직접판매와 다르다. 그대로 베끼면 실제 운영과
어긋난다.

| 조 | 내용 |
| --- | --- |
| 제1조 | 목적 |
| 제2조 | 정의 (회원 · 구매대행 · 마켓) |
| 제3조 | 약관의 명시와 개정 |
| 제4조 | 서비스의 제공 및 변경 |
| 제5조 | 회원가입과 계정 |
| 제6조 | 회원 탈퇴 및 이용 제한 |
| 제7조 | 구매 신청과 계약의 성립 |
| 제8조 | 대금 지급 |
| 제9조 | 배송 (마켓별로 다름 — 일본은 구매대행) |
| 제10조 | 청약철회 및 반품 |
| 제11조 | 환급 |
| 제12조 | 개인정보 보호 (처리방침으로 위임) |
| 제13조 | 분쟁 해결과 관할 |

### 개인정보처리방침 (`privacy`)

| 항 | 내용 |
| --- | --- |
| 1 | 수집하는 항목과 수집 방법 (가입 · 주문 · 소셜 로그인) |
| 2 | 이용 목적 |
| 3 | 보유 및 이용 기간 (전자상거래법상 보존 의무 포함) |
| 4 | 제3자 제공 |
| 5 | 처리 위탁 (Supabase · 결제대행사 · 배송사) |
| 6 | 국외 이전 (Supabase 리전 확인 후 기재) |
| 7 | 정보주체의 권리와 행사 방법 |
| 8 | 파기 절차와 방법 |
| 9 | 안전성 확보 조치 |
| 10 | 개인정보 보호책임자 |
| 11 | 쿠키 등 자동 수집 장치 |
| 12 | 처리방침 변경 고지 |

**실제로 수집하는 항목과 일치해야 한다.** 코드 기준으로 현재 수집하는 것은

- 가입: 이메일, 비밀번호(해시), 이름
- 소셜 로그인: 제공자가 주는 이메일·이름
- 주문: 받는 분, 후리가나(일본), 전화번호, 이메일, 주소, 배송 메모
- 동의 기록: 약관·개인정보·마케팅 동의 여부와 시각

문서를 쓸 때 이 목록을 코드로 다시 확인한다. 실제와 다르면 그 자체가 위반이다.

### 일본어판

`利用規約`과 `プライバシーポリシー`. 한국어판의 번역이 아니라 **같은 사실을 일본 관행에 맞춰**
쓴다. 다만 CLAUDE.md에 따라 개인정보 관련 요건은 양국 중 엄격한 쪽(한국 기준)을 따르므로,
수집 항목·보유 기간·권리 행사 부분은 한국어판과 내용이 같아야 한다.

| 파일 | 무엇을 |

| `src/app/[market]/(main)/terms/page.tsx` | 「준비 중」 → `LegalDocumentBody` |

`features/consent-form`(소셜 로그인 후 동의 화면)도 같은 모달을 쓴다. 지금 그 화면에 약관 링크가
있는지 구현할 때 확인하고, 없으면 추가한다.

## 검증

- `findPlaceholders`가 미입력 항목을 빠짐없이 찾는지 (순수 함수 테스트)
- 두 로케일의 문서가 **같은 조항 수·같은 `version`**을 갖는지. 한쪽만 고치는 사고를 막는다
- 개인정보처리방침의 수집 항목이 실제 코드와 어긋나지 않는지 — 이건 자동화가 어려우니
  문서에 확인 시점을 남긴다
- 브라우저: 가입 화면에서 모달을 열고 닫아도 **입력값이 남아 있는지**, 모바일 뒤로가기가
  모달만 닫는지, 페이지 직접 접속이 되는지, 푸터 링크가 동작하는지

## 범위 밖

**약관 개정과 재동의.** `user_consents.terms_version`이 기본값 `'v1'`이고 이번 문서도 v1이라
지금은 맞는다. 개정할 때는 버전을 올리고 기존 회원에게 재동의를 받는 흐름이 필요한데, 그건
마이그레이션과 화면이 따로 필요한 별개 작업이다.

**일본 特定商取引法に基づく表記.** 일본에서 판매하려면 별도 페이지가 필요하다. 사업자 정보가
확정돼야 쓸 수 있고, 문서 성격도 약관과 달라 같이 묶으면 커진다.

**청약철회 실제 운영 규칙.** 반품 배송비 부담 주체, 구매대행 상품의 철회 가능 범위 등은
운영 정책이 정해져야 문서에 적을 수 있다. 초안에는 법정 최소 기준으로 적고 빈칸으로 표시한다.
